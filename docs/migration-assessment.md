## 4. DBの選定

| 観点 | SQLite | PostgreSQL |
|---|---|---|
| 適した規模 | 1アプリ・少人数・短い書込 | 同時更新や複数サービスが増える構成 |
| 運用 | アプリと同じVPSのローカルファイル。DBサーバー管理が不要 | DBサービス、利用者・権限、更新・監視の管理が必要 |
| 同時書込 | 同時に1書込。短いトランザクションで順番待ち | 複数更新を扱いやすい。競合設計自体は必要 |
| 他アプリ連携 | API経由なら可能。DBファイルを共有フォルダーに置かない | API連携、権限分離、集計・連携基盤を拡張しやすい |
| バックアップ | Online Backup API等で整合したコピーを作る | pg_dump、必要に応じてWAL保管による時点復元 |
| 初期費用・手間 | 小さめ | SQLiteより設定・運用の手間が増える |

PostgreSQLを使う場合も、n8nや他社のDBとテーブルを混在させず、資金繰り用のDB・専用権限を分ける。既存のPostgreSQLがあるという理由だけで、他アプリの内部DBへ書き込まない。

他アプリとの連携は、保存先を問わず、取引ID・変更版・再送IDを持つAPIで行う。受注アプリから確定した請求・支払予定を受け、資金繰りから決済状態を返す境界を決める。DBを直接共有して相互に更新する方式は避ける。

SQLiteの適性・同時書込の制約は[公式説明](https://www.sqlite.org/whentouse.html)を確認した。PostgreSQLの将来性だけを理由にSQLiteを不適切とは判断しない。

## 6. バックアップ・復元案

以下は**提案**であり、現在稼働しているバックアップの保証ではない。

### VPS共通

1. データとアプリを分離し、再配備で消えない永続保存先を指定。
2. 初期案は1時間ごとの整合バックアップ。時間単位を7日、日次を30日、月次を12か月保持。
3. VPS内の控えに加え、暗号化して別サービス・別保管先へ複製。同一VPSだけに置かない。
4. 成否と最終成功時刻を監視。失敗、2時間以上の未取得、容量不足を通知。
5. 初回運用前と月1回、隔離した検証DBへ復元。件数、売掛・買掛残、口座残高、決済ID重複、画面・Excelを照合。
6. アプリの版・DBスキーマ版・復元手順・必要設定を残す。秘密設定はDBとは別に安全に保管。

初期の目標案：失ってよい更新は最大1時間、復旧は4時間以内。実際に達成できるかは容量・外部保存・復元試験で確認する。これより短い損失許容ならPostgreSQLのWAL継続保管を検討する。

### SQLite

稼働中の `.sqlite` ファイルだけを単純コピーしない。WALモードでは未反映の更新が別ファイルにある。Online Backup API／対応するバックアップコマンドで整合スナップショットを作り、整合性検査後に外部保存する。[SQLite公式バックアップ説明](https://www.sqlite.org/backup.html)

### PostgreSQL

小規模では `pg_dump` のカスタム形式を定期取得し、`pg_restore` で別DBへ復元検証する。DBロール等の再作成情報も別途管理する。ダンプは任意時点への復元ではない。任意時点復元を求める場合はベースバックアップ＋WAL保管を追加する。[公式ダンプ説明](https://www.postgresql.org/docs/current/backup-dump.html)、[WALと時点復元](https://www.postgresql.org/docs/current/continuous-archiving.html)

### Google構成

Driveの変更履歴だけをバックアップと見なさず、時間トリガー等で運用ブックの独立コピーを定期取得する仕組みを新規実装する。アプリの書込と競合しないようロック・取得版を管理し、別保管先への周期的な複製も用意する。復元時はコピー先IDの切替とApps Script再接続・権限確認が必要。

画面の「Excel出力」は、表示月・選択口座の帳票だけである。取引先、口座基準日、売掛・買掛原本、固定支出等を全部含むDBバックアップの代わりにはならない。

## 7. 比較と工数

| 観点 | Googleを継続 | VPSへ移行 |
|---|---|---|
| 開始まで | 保存環境は既存技術を利用できる | バックエンド・DB・配備が必要 |
| サーバー保守 | Google側が基盤を管理 | OS・Node.js・DB・TLS・容量・監視を管理 |
| 更新の整合性 | Sheets API一括更新とアプリロック。シート直接編集はロック外 | DBトランザクション・制約を利用できる |
| アクセス制御 | Googleアカウント・GASの公開方式との整合が必要 | 利用者ログイン・権限をアプリとして整備できる |
| バックアップ | 自動コピー・復元接続の仕組みを追加 | DBバックアップ・外部保存・復元を標準化しやすい |
| 他アプリ連携 | 可能だがGASの実行制限・認証境界を考慮 | API連携と共通監視・運用を整えやすい |
| 長期の変更 | 画面・GAS・シート列の3か所を合わせる | ソース・DB移行の管理に集約しやすい |
| 主な弱点 | 直接編集による不整合、実行制限、認証付き別オリジン通信 | 基盤の保守責任、同じVPSの障害の影響、運用工数 |

### 運用先決定後の残作業の概算

| 案 | 残作業の目安 | 主な作業 |
|---|---|---|
| Google構成 | 2～4人日 | 実Google環境での一括保存検証、ログインと画面配信方式、バックアップ、復元、受入確認 |
| VPS + SQLite | 4～7人日 | Node.js移植、DB・認証、配備、バックアップ・復元、受入確認 |
| VPS + PostgreSQL | 5～9人日 | 上記に加えてDB接続・ロール・運用設定・競合検証 |

1人日は担当者1名の約6～8時間の実作業を想定した粗い見積り。納期の約束ではない。既存の認証・配備・バックアップ基盤を再利用できれば短縮し、VPSの構成整理が必要なら増える。今回のローカル不具合修正は上記の残作業とは別で、既に実施した。専用PDF、実データ移行、他アプリとの本格連携、銀行自動取得は含まない。

他アプリ連携の初回実装は契約と認証が未確定のため別見積り。単方向の単純な連携でも、再送・重複・取消まで含め2～4人日程度を仮置きする。双方のAPIが未実装なら増える。

## 今回の不具合修正と検証範囲

- 月をまたぐ30日予測、過去・未来の月初残高、0円実績、予定月と実績月の二重計上を修正。
- 残高を「基準日の終了残高」として扱う。翌日の実績を反映できる。基準日以前の残高を再現するには、その期間の取引履歴が必要。
- 期限超過の未決済分は、今日の見込みへ仮置きして予測から消えないようにする。確実な入出金日ではないため、予定日は運用で更新する。
- 売掛・買掛・関連予定・決済履歴を一括保存。保存途中の失敗で片方だけ残る経路をなくした。
- 分割入金・支払は別々の実績行として保存。再送による同一決済の二重登録を防止。
- 部分更新で未指定項目を空にしない。更新版の照合で古い画面からの上書きを拒否。
- 未決済の売掛・買掛削除は関連予定も削除。確定実績のある原本や使用中口座の削除を拒否。
- デモモードで保存成功と見せない。0円実績は手動取引で登録可能。

ローカル自動テストとブラウザー検証は `verification.md` を参照。**実Google APIへの書込、本番VPS、ログイン・権限、バックアップの復元は未検証。現在の修正版をそのまま本番公開してよいという判定ではない。**
