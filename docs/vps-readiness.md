確認日：2026-09-18 14時台 JST。SSHによる読み取り調査。既存サービスの停止・設定変更・DB変更なし。新アプリの実装・配備なし。

## 判定

**Node.js + SQLiteで進めてよい。** 利用者1人、単一アプリからローカルDBへ接続し、将来の連携もAPI経由とする条件に合う。これは構成選定の判断であり、本番運用開始OKの判断ではない。負荷値は調査時点の瞬間値で、ピーク時の保証ではない。

## 2. 採用する構成案と変更範囲（未実装）

- 新しい独立Composeプロジェクト、Node.js 24 LTS系の検証済みパッチ版・イメージdigest固定、アプリ1インスタンス。初期上限1 CPU / 512 MiB、ログ上限を設定し実測で調整。
- HTTPS入口は既存Caddy。新アプリ専用ホスト名を追加し、edgeネットワークから接続。新しい公開DBポートは作らない。
- **Caddyのルート追加・再読込は既存共有設定への変更なので、具体的な差分を提示して事前確認を得てから実施。** ホスト名・DNSも実装前に確定。既存Compose全体の再起動は不要な設計とする。
- ソース・配備定義は /opt/wfs/cashflow、DBは新設 /srv/wfs/cashflow/data を /var/lib/cashflow へbind mountする案。DB本体・WAL・SHMを同じ永続ディレクトリに置き、コンテナの再作成とデータ削除を分離する。所有者を専用実行UIDに限定し、配備手順に当該ディレクトリ削除を含めない。
- SQLiteはWAL、foreign_keys=ON、synchronous=FULL、busy_timeoutを各接続で設定。短いトランザクション、決済IDの一意制約、更新競合チェックを実装。
- 画面と残高計算は再利用。GAS接続を同一オリジンのNode APIへ置換し、全7表の保存・業務処理を移植。関連更新はDBトランザクションにする。
- 認証：単一管理者、パスワードハッシュ、サーバー側セッション、Secure/HttpOnly/SameSite Cookie、CSRF対策、試行制限。全APIで認証・権限を検査。公開ユーザー登録なし。将来の連携は用途別・権限別トークンを追加し、ブラウザーの管理者セッションを流用しない。
- Excelは既存のブラウザー出力を維持し、API移植後に実ファイルを再検証。専用PDF機能は現状存在せず、新機能として必要なら別途実装範囲を定める。

### 将来のAPI連携とPostgreSQL

他アプリはHTTPS APIを通じて読み書きし、SQLiteファイルを直接共有しない。API連携だけを理由にPostgreSQLへ変える必要はない。ただし大量の同時書込み、複数VPSへの水平展開、高可用性が必要なら再検討する。

現状cloneはGAS保存層なので、**まだPostgreSQLへ差し替え可能な実装が完成しているわけではない**。移植時に業務処理・API・DBアクセスを分離し、リポジトリ境界とバージョン付きスキーマ移行を設ける。金額は整数円、ID・日付形式を統一し、SQLite固有SQLをDB層に限定。将来は書込み停止→整合スナップショット→変換取込→件数・金額・関連ID照合→接続切替。移行実装・検証自体は別途必要。

## 3. バックアップ設計案

|項目|設計|
|---|---|
|取得|SQLite Online Backup API（Nodeのsqlite.backup）で別ファイルへ整合スナップショット。稼働中DBファイルの単純コピーは禁止。WAL内のコミット済み内容もSQLite経由で取得|
|検証|一時名へ作成後、integrity_check / foreign_key_check、業務整合性検査。スナップショットから各表件数・残高・未決済額・スキーマ版・アプリ版をmanifest化し、SHA-256付与。完成分のみ公開名に変更|
|頻度|毎時17分と配備・スキーマ変更前。重複実行ロックと実行時間上限。既存03:15/03:25と同時実行を避けるためバックアップ処理は帯域・CPU制限も設定|
|ローカル保存|/var/backups/wfs/cashflow。時間単位48時間＋日次7日|
|外部保存先|Google Driveの専用 WFS Backup/cashflow フォルダ案。既存の外部バックアップ準備方針に合わせるが、認証・容量・所有者・実転送は未確認。OAuth設定完了と接続試験を本番開始条件とする|
|暗号化・転送|age公開鍵で暗号化後、rcloneで世代別にcopy。syncで削除を伝播させない。復号秘密鍵はVPSに常置せず、パスワード管理庫と別のオフライン媒体に保管|
|外部保存期間|毎時7日、日次30日、月次12か月。最終正常世代を必ず保持。専用フォルダ内のみ世代削除し、他アプリ領域は触らない|
|転送検証|転送完了後、外部ファイルを読み戻して暗号化ファイルのSHA-256を照合。照合完了を成功条件にする。再試行は最大3回。失敗時に正常世代を削除しない|
|失敗検知|VPS外の監視サービスに、検証済み外部保存成功時だけheartbeatを送る。90分成功通知なし・明示失敗をメール通知する設計。監視サービスと通知先は未確定、実装前に選定。VPS内のn8nだけに監視を依存させない|
|復元目標|正常に毎時外部保存できている場合、失う更新は概ね最大1時間。復旧4時間以内を仮目標とし、復元訓練で実測して確定|

DB以外に再配備用コード・固定イメージ情報・スキーマ移行・運用手順を外部保管する。認証設定等の必要な秘密情報は別の暗号化保管で復旧可能にする。ブラウザーlocalStorageに残る会社名なども設定移行対象を明確にする。DriveのOAuth失効・容量不足・監視停止も試験対象。

## 4. 実際の復元手順と本番開始条件

1. 外部保存から対象世代の暗号化バックアップ・manifest・チェックサムを取得。チェックサム照合、VPS外の鍵で復号。ローカルの残存DBを代用しない。
2. 同じアプリ版・スキーマ版を新しい隔離環境へ配備。空の別データディレクトリに復元し、外部連携を無効にする。既存アプリや既存DBには触れない。
3. SQLite integrity_check / foreign_key_checkを実施。全7表の件数、売掛・買掛の未決済合計、決済累計、口座基準残高、日繰りの予定・実績・予測残高、関連IDをmanifestと照合。
4. 認証して画面確認。分割決済・再送による二重登録防止・関連更新・残高予測・Excel出力を検証し、コンテナ再作成後も復元データが残ることを確認。
5. 本番前はまだ業務データがないため、売掛・買掛・複数口座・月跨ぎ・分割決済を含むテストデータで**実際の外部バックアップ→ダウンロード→復元**を完遂する。空DBの復元だけで合格にしない。WALに未checkpointのコミット済み更新がある状況でも欠落がないことを試験する。
6. 本番障害時の切替は、資金繰りアプリだけ書込みを停止し、旧データを退避した上で検証済み復元領域へ接続を切り替える。古いWAL/SHMを復元DBに混在させない。起動・認証・帳尻確認後に再開する。
7. 復元所要時間・取得世代・照合結果・不足設定をverification.mdへ記録。本番開始前に、外部転送失敗・未着通知、ディスク永続化、実環境の既存サービスへの影響を確認する。
