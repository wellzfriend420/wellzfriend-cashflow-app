# VPS版 実装・運用計画（2026-09-24）

2026-09-25更新：アプリ0.3.0／SQLite v2では口座の旧nameを廃止し、bank・branch・type・accountNumberへ整理。更新前に旧版Backup APIで退避を取り、新版で復元・移行を検証してから資金繰りapp／backupだけを更新する。旧版バックアップは復元先側だけv2へ移行する。残高、参照ID、認証情報は維持する。

対象はウェルノット資金繰りのみ。既存 wf-production の n8n、PostgreSQL、Caddy、受注／利益管理を変更しない。Google Drive共通バックアップは今回の実装条件から外す。本書は以前のGAS手順・VPS準備資料より優先する。

## 構成と受入条件

- Node.js 24.18.0、公式Dockerイメージをダイジェスト固定。追加のサーバーnpm依存なし。
- `src/domain/ledger.cjs` は資金繰り業務処理、`src/storage.cjs` はSQLite保存層、`src/server.cjs` はHTTP境界。将来PostgreSQLへ移す場合は保存層・非同期インターフェイス・移行処理を置換し、同じ業務回帰試験を適用する。
- 7業務テーブル、整数円、安定ID、外部キー、トランザクション、更新版の照合。売掛／買掛と予定を同時更新し、分割決済は個別実績として保存。別アプリは認証されたAPIで連携する。今回、他アプリへの連携やサービス用APIトークン発行は行わない。
- ホーム、日繰り予測／実績／差異、売掛、買掛、口座、会社名、取引先、固定支出、Excel出力を移植。GAS URL入力・デモ保存先・外部CDNを除去。
- 本番DBは空で開始し、既存スプレッドシートや他アプリから実データを自動転記しない。実データ移行が必要な場合は別途対象・対応関係を確定する。

| 用途 | VPSパス・制限 |
|---|---|
| ソース・Compose | `/opt/wfs/cashflow` |
| 専用SQLite | `/srv/wfs/cashflow/data/cashflow.sqlite` |
| 整合バックアップ | `/var/backups/wfs/cashflow` |
| 取得状態・排他ロック | `/srv/wfs/cashflow/backup-status` |
| アプリ | 1 CPU / 512 MiB、非root、読み取り専用ルート、専用ネットワーク |
| バックアップ | 0.25 CPU / 256 MiB、非root、ネットワークなし、元DBマウントは読み取り専用 |
| 仮の接続先 | `127.0.0.1:3310` のみ。SSHトンネルで確認 |

## 認証・アクセス制御

管理者1名から開始。既定パスワードなし。12〜256文字のパスワードをscrypt（N=32768/r=8/p=1、ランダムsalt）で保存する。セッションはランダム値のハッシュのみDBへ保存し、HttpOnly/SameSite=Strict Cookie、HTTPS公開時はSecureと`__Host-`を使用。8時間の絶対期限、1時間の未操作期限、新規ログイン・パスワード変更で旧セッションを失効する。

すべての業務APIはログイン必須。変更操作にはOrigin・CSRF照合、ログインには永続的な試行制限を適用。生のパスワード、トークン、業務本文をログへ記録しない。静的ファイルは明示的な許可リストのみ公開。入力文字列はHTML表示時にエスケープする。既存画面のイベント属性は維持しているため、CSPは同一サイトのスクリプトとインラインイベント属性を許可する。新規コードでインラインイベントを増やさない。

共有プロキシ配下ではIP制限が利用者共通になる（転送ヘッダーを無条件に信用しない）。低人数の初期運用では安全側の制限。利用者増加時はプロキシの信頼範囲・利用者管理を設計してから変更する。

初期管理者は利用者本人がローカルPowerShellで次を実行し、非表示入力でパスワードを設定する。パスワードをコマンド引数・チャットに記載しない。

```powershell
.\tools\create-admin.ps1 -SshTarget root@85.131.245.115 -IdentityFile C:\Users\tnaka\.ssh\enchan_vps_ed25519 -Username admin
```

登録済みの場合、このツールは上書きを拒否する。登録後の変更は画面内の「パスワード変更」を使う。管理者を追加・再設定する場合は承認された保守作業として扱う。

## VPS内バックアップ

専用backupコンテナ起動直後と毎時17分に取得。既存の3:15／3:25のバックアップと時刻をずらす。SQLite Backup API（`node:sqlite.backup`）を使い、稼働中DBの単純コピーは行わない。

1. 排他ロックを取得し、別領域の一時ファイルに整合スナップショットを作る。
2. `integrity_check`、外部キー、売掛・買掛の決済額／残額整合、スキーマ版を確認。
3. SHA-256、サイズ、件数・集計、アプリ／スキーマ版を記録。
4. 本体を確定し、最後にmanifestを書いて完了扱いにする。
5. 正常取得後にのみ世代を整理。毎時48世代＋日本時間の日次14世代（重複は共有、通常約60本）。欠測時は取得できた世代を残すので、厳密な経過時間だけによる全削除はしない。

DB本体、`.sha256`、`.manifest.json` の3点で1組。将来の外部バックアップは、完成manifestのある組を一緒に暗号化して転送する。manifestには集計値があるため、これも暗号化対象。外部保管先の認証、鍵、容量監視は今回未実装。

失敗・取得なし・最終成功から90分超過をログイン後の画面へ表示し、コンテナのヘルスチェックも失敗させる。標準出力には成功ID・サイズまたは一般化した失敗コードだけを出す。バックアップ状態のディレクトリを保存先と分け、保存先障害でも状態を残しやすくする。メール等への外部通知は未設定。現段階では画面または運用チェックで確認する。

```sh
docker compose --project-directory /opt/wfs/cashflow ps
docker compose --project-directory /opt/wfs/cashflow exec -T backup node tools/backup-status.cjs
docker compose --project-directory /opt/wfs/cashflow logs --tail 30 backup
```

10分で完了しない取得は中断し、失敗状態を残す。異常終了時に残った`backup.lock`は勝手に削除しない。資金繰りbackupコンテナだけを停止し、取得プロセスが終了していることを確認してから、当該ロックだけを削除し再開する。既存サービスを止める必要はない。

アプリ稼働中は元DBのWAL/SHMも存在する。バックアップ処理が参照するため専用dataディレクトリ全体を読み取り専用マウントし、ファイルだけをバインドしない。バックアップ済みSQLiteは独立した復元元として検証する。

Backup API完了後、取得した一時スナップショット側だけをDELETEジャーナル形式へ整え、WAL/SHMが不要な単独ファイルとして確定する。稼働中の元DBのジャーナル形式は変更しない。

## 復元と定期試験

`tools/restore.cjs <manifest.json> <新しいDBパス>` はチェックサム・サイズ・構造・整合性を確認し、存在しない復元先だけにBackup APIで復元する。既存DBやWAL/SHMがあれば拒否。復元先のログインセッション・試行制限を消し、必ず再ログインさせる。口座、予定、決済履歴、設定、管理者ハッシュは維持する。

月1回と更新前に、専用の一時領域へ復元し、本番とは別のネットワークなしコンテナで整合性・件数・金額集計を照合する。定期試験の自動実行は次の運用整備で追加する。現時点でバックアップの自動取得・都度検査は実装済み。初回は実装時に手動で復元試験を実施する。

災害復旧では、資金繰りアプリだけを停止→旧dataを保全→空の新dataへ復元→権限1000:1000/600を確認→同じアプリ版で起動→再ログイン→件数・残高・分割決済・固定支出・Excelを確認する。既存DBへの直接上書きやバックアップ元の変更は禁止。復旧中に既存n8n・PostgreSQL・受注アプリを操作しない。

VPS内の別ディレクトリは、VPS全損に対する保護ではない。本番入力開始時にこの残存リスクを共有し、別途予定している暗号化外部バックアップへつなぐ。今回の移植を外部バックアップ未導入で止めることはしない。

## 公開前の確認と変更境界

- Linuxコンテナ上でSQLite・HTTP・バックアップ／復元の試験を通す。
- 空の専用DBと初回バックアップ、専用コンテナのヘルスを確認。
- 既存4コンテナのID・起動時刻・状態とCaddyファイルのハッシュが変更前と同じであることを確認。
- 利用者が初期管理者を設定し、合成データで操作確認する。
- 公開用ホスト名の決定後、Caddyに追加する**1サイト分だけ**の差分、資金繰りのネットワーク接続、PUBLIC_ORIGINのHTTPS変更を提示し、承認後に実施する。Caddyの既存サイト設定を置換しない。
- DNS・Caddy・既存サービス／DBの変更は今回の独立配置に含めない。

確認用SSHトンネル（ローカル3310が空いている状態）：

```powershell
ssh -N -L 127.0.0.1:3310:127.0.0.1:3310 -i C:\Users\tnaka\.ssh\enchan_vps_ed25519 -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UpdateHostKeys=no root@85.131.245.115
```

接続後にブラウザーで `http://127.0.0.1:3310` を開く。将来HTTPS公開するとCookieとOriginが変わるため再ログインが必要。
