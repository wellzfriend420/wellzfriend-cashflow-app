# 確定実績の訂正・取消 0.6.0（本番未反映）

## 0.5.0からの変更

| 確認項目 | 現行0.5.0 | 0.6.0候補 |
|---|---|---|
| 1. 現在可能な操作 | 予定の編集、全額／売掛買掛の分割実績化。確定実績の直接編集・削除は拒否 | 既存操作を維持 |
| 2. 追加操作 | 訂正専用処理なし | 管理者専用の実績訂正・取消・元予定への確定解除、履歴参照 |
| 3. 編集方法 | 不可 | 日繰りの実績を開く→実績のまま訂正→理由入力→変更前後確認→保存。実績日・金額・口座・取引先・摘要・メモを変更。手動／Excel実績は入出金区分も変更可 |
| 4. 取消／削除 | 確定実績は拒否 | 物理削除しない。明細IDを維持して取消状態とし、実績日・実績額を集計対象から除外。以前の値は変更不能の履歴に保存。確認画面と理由必須 |
| 5. 元予定への解除 | 不可 | 手動予定・固定支出・予定表は保存された元予定へ復帰。売掛／買掛は決済明細を取消し、元債権債務の未決済残額へ戻す。Excel移行実績／新規の直接確定実績には提供しない |
| 6. 残高 | 基準日の終了残高から全実績を集計 | 同じ計算を維持。日付・金額・区分・口座変更と取消を即時反映。口座変更は両口座へ反映 |
| 7. 借入／定期支出 | 元本・利息を持つ実績は保護 | 同一DBトランザクションで銀行実績・元本・利息・親バージョンを更新。銀行合計＝元本＋利息。別引落は対象側だけ更新。完了状態・残元本・支払利息は最新実績から再計算 |
| 8. Excel移行元 | 完了設定・固定ID・メモ | 移行ID／原本ハッシュ／原本名／シート／セル／移行時明細を変更不能の専用表に分離。利用者がメモを変更しても失わない |
| 9. 再インポート | 原本と現在明細が完全一致することを照合 | 新しい実行ツールは完了案件・ペイロードハッシュ・不変の元明細ID／座標を照合。訂正・取消後も追加0件、口座作成0、開始残高更新0。旧ツールはschema4を拒否して安全停止 |
| 10. 訂正履歴 | 操作名・操作者・対象IDのみの監査 | 専用表へ操作者ID／当時のユーザー名／時刻／理由／操作／変更前後の実績と関連データを記録。既存監査にも記録。日繰りの「実績の訂正・取消履歴」から取消後も参照可能 |

## 整合性と制限

- `correctActual` / `cancelActual` / `reopenActual` は管理者認証、Origin・CSRF検査の既存APIを使用。操作者はセッションから決定し、本文から指定できない。
- 明細の更新時刻と、関連予定表のバージョン／売掛買掛の更新時刻で競合を拒否。操作IDによる同一内容の再送は結果のみ返し、履歴も重複させない。
- 実績更新・関連元本利息／決済済額・履歴・監査は同一の `BEGIN IMMEDIATE` 内で保存。どれか失敗すると全体が戻る。
- 自動生成元の区分・関連ID・予定額・予定日は実績訂正画面では変更不可。売掛／買掛・固定支出・予定表の入出金区分は固定。異なる種類の取引に変更する場合は元明細の取消と適切な種類での登録を行う。
- 銀行残高基準日以前、または借入元本基準日以前に関わる金額・日付等の変更では、基準残高を自動更新しない旨の確認が必須。基準翌日以後だけが積み上げに含まれる。基準以前の訂正を現在残高へ自動加算する処理は行わない。
- 借入の実績元本は実績日の属する基準後期間だけ残元本から差し引く。実績利息は実績日までの累計。予定元本では減らさない。
- 借入の片側取消では、相手の元本／利息実績・予定を維持。「一部支払」「一部支払・残予定取消」「一部取消」を区別する。
- 売掛／買掛の実績取消は請求・債務の取消ではない。取消額は未決済残額へ戻り、残額予定が増える。この点を画面でも明示する。
- 一度実績化した後に解除した元予定は、初回確定前の予定を保持し、マスタ再生成・通常編集・物理削除から保護する。元予定で再確定し、実績訂正で変更できる。相手側の未実績の借入明細は従来どおり変更可能。
- 取消済み実績の復活専用ボタンは今回含めない。履歴は保存・参照可能。取消・確定解除には二段階の確認を設ける。
- 履歴一覧は新しい500操作まで。各明細の詳細は全履歴を表示する。

## DB更新（schema3 → schema4）

1. `transaction_origins`: transactionId PK/FK、kind、migrationId、fileHash、sourceFile、sheet、cell、originalJson、planJson、createdAt。移行ID＋ハッシュ＋シート＋セルはUNIQUE。更新／削除は禁止トリガーで保護する。
2. `transaction_revisions`: requestId PK、requestHash、transactionId FK、action、actorId、actorName、reason、beforeJson、afterJson、createdAt。更新／削除は禁止。JSONには元本・利息・元予定の更新前後も含める。
3. 移行完了設定の265個のIDとメモ内の座標・ハッシュを照合して移行元情報を追加する。取引・口座・管理者・既存予定の値は変更しない。照合失敗時はschemaも含めてロールバックする。
4. 0.5.0で確定済みの通常明細は最初の訂正時に元データを保存。既存の手動明細は予定日・予定額がある場合だけ元予定として扱う。今回のExcel移行分は専用の不変情報により必ず除外する。

## バックアップ／復旧

新しいバックアップ処理は履歴・移行元表を含むDB全体を保存し、参照整合性・移行元情報・借入・債権債務整合性を検査する。旧schema1〜3のバックアップも隔離先へ復元して更新可能。

**本番反映前に停止。** 今回はローカル実装と検証のみ。将来の反映時は直前の整合バックアップを0.5.0で取得し、checksum・manifest・隔離復元・旧版復旧可能性を確認した後、アプリとバックアップサービスを同時に0.6.0へ更新する。現在の本番DBへこの検証コピーを置かない。

0.5.0はschema4を拒否するため、イメージだけを戻すことはできない。復旧時は書込みを止め、schema4の失敗時DBを保存したうえで、反映直前のschema3バックアップから0.5.0へ戻す。反映後に利用者が入力したデータは旧バックアップには含まれないため、その間のデータを破棄する自動復旧はしない。今回、隔離環境で旧版起動と元283件の保持を検証した。
